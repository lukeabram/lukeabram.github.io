A. Microarchitecture

Owner: Luke Abram. Covers SM organization, the register file, warp processing units, functional units, fifth-generation tensor cores and TMEM, and scheduling.

Start with the Blackwell Tuning Guide, §1.4.1, for the official per-SM limits. Then read §III-A and §V-A of Jarmusch and Chandrasekaran (2026) for chip organization and Tensor Memory as measured on a B200. For how the tensor cores are actually driven, the CUTLASS tcgen05 guide is the clearest source; read “Global Memory (GMEM) to MMA data flow overview” first, then the CtaGroup.TWO section.

For instruction issue and the unified INT32/FP32 units, the only public measurements are in Jarmusch, Graddon and Chandrasekaran (2025), §IV-B and §IV-D. That paper tests the consumer GB203, so treat its results as evidence about the Blackwell SM in general, not about B200. The Cornell Virtual Workshop is a useful check on your reading of the SM diagram.

What we found

TopicFindingSource
Chip organizationTwo dies, each with 80 SMs physically present and 74 enabled, for 148 of 160 SMs enabled. The SMs are spread across 8 GPCs. The chip has 4 L2 partitions (twice Hopper’s count) and 8 HBM3e stacks, and the two dies are joined by NV-HBI.Chips and Cheese; Jarmusch 2026, §III-A
SM sub-partitions4 per SM. Each has an L0 instruction cache, a warp scheduler, a dispatch unit (32 threads/clk), a 16,384 × 32-bit register file slice, 64 KB of TMEM, CUDA cores, a tensor core, LD/ST units, and an SFU. Shared across the SM: the Tensor Memory Accelerator, 256 KB of L1/shared memory, and texture units.Whitepaper; Cornell CVW
Register file and occupancy64K 32-bit registers per SM, at most 255 per thread, and at most 32 blocks and 64 warps per SM. A thread that uses all 255 registers needs 8,160 registers per warp, which allows only 8 such warps per SM. Heavy register use therefore caps occupancy well below the block limit.Tuning Guide, §1.4.1.1
Functional unitsINT32 and FP32 appear to share unified units, based on the GB203 measurements. The SFU handles transcendental functions such as sine and exp. Tile size changed throughput but not latency, which suggests wider functional units.Jarmusch 2025, §IV-B (GB203)
Tensor Memory256 KB per SM, organized as 512 columns × 128 lanes of 32-bit cells. Each sub-partition owns 32 lanes, and a warp can access only its own 32. TMEM is allocated and freed explicitly with tcgen05.alloc and tcgen05.dealloc.Jarmusch 2026, §V-A; PTX ISA, §9.7.18.1
tcgen05 versus Hopper WGMMAOn Hopper, a whole warpgroup issues WGMMA in lockstep and the accumulators sit in registers. On Blackwell, a single thread issues tcgen05.mma. Operands come from shared memory or TMEM, and the accumulator always lives in TMEM, which frees the register file.PTX ISA, §9.7.18.5 and §9.7.18.10; CUTLASS tcgen05
CTA pair (2-SM MMA)Two CTAs on paired SMs work on one tile. Each holds half of the A rows and owns half of the output C in its own TMEM. Each also stores half of B and reads the other half from its peer through distributed shared memory. The usable tile size is therefore no longer limited by one SM’s shared memory.CUTLASS tcgen05, “CtaGroup.TWO”
Number formatsFP64, FP32, TF32, FP16, BF16, FP8, INT8, FP6, and FP4. Block-scaled (microscaling) formats give each small contiguous block, such as 16 or 32 elements, its own scale factor. For example, MXFP8 turns 32 FP32 values into 32 FP8 values plus one shared scale. Its scales are power-of-two E8M0 values, and the 32-element block matches the tensor core design.cuDNN Block Scaling; FP8 scaling blog; CUTLASS SM100
Scheduling hierarchyThreads are grouped into warps, warps into CTAs (thread blocks), and CTAs into clusters. A cluster lets its CTAs read, write, and perform atomics on each other’s shared memory across SMs (distributed shared memory). The warp scheduler issues one warp instruction per clock per sub-partition.CUDA Guide, §1.2; Tuning Guide, §1.4.1.2
Issue policy (not documented by NVIDIA)Throughput rises smoothly as independent instructions are added, more evenly than on GH100. This points to a conservative issue strategy tuned for regular, high-ILP kernels. The result is inferred from microbenchmarks only.Jarmusch 2025, §IV-D (GB203)
Where the speedup comes fromTraining speedup over H200 breaks down into SM count (1.09×), CTA pairing (1.27×), and TMEM (1.26×). TMEM latency and bandwidth explain the faster attention accumulation.Jarmusch 2026, §VII-D

B. ISA and memory consistency

Owner: Aidan. Covers the two-level ISA (PTX and SASS), Blackwell-specific instructions, and the memory consistency model.

The PTX ISA manual is the reference throughout. For the instruction set, read §9.7.18 (the tcgen05 family), §5.5.8 (tensor maps used by TMA), and §9.7.15.16 (mbarrier). For the memory model, read chapter 8 in order: scopes (§8.5), proxies (§8.6), morally strong operations (§8.7), and release/acquire patterns (§8.8). §9.7.18.6 adds the tcgen05-specific ordering rules. These define where fences belong in a TMA → tensor core → TMEM pipeline.

The CUDA Programming Guide covers the same features from C++. Use §5.1 to explain what sm_100 and sm_100a mean, and §4.11 and §4.13 for asynchronous barriers and copies. For the theory behind scoped memory models, read Lustig et al. (ASPLOS 2019).

C. Memory system and interconnect

Owner: Pranav. Covers the chip overview, cache organization, DRAM organization, the CPU interface, and the GPU-to-GPU interconnect.

For official capacities, start with §1.4.2 of the Tuning Guide. It gives the 256 KB unified L1/shared memory, carve-outs up to 228 KB, and the 126 MB L2. For measured behavior, read “Cache and Memory Access” and “Bandwidth Measurements” in Chips and Cheese. That article shows the latency jump when a working set spills from the near L2 partition to the far one, and notes that most of the L2 is reachable without cross-partition penalties only when many threads are running.

For the dual-die design and NV-HBI, use the whitepaper and the Hot Chips 2024 slides. For NVLink 5 and the HGX B200 board, use the NVLink and HGX pages for headline numbers. For how a B200 fits into a server, use the Components chapter of the HGX AI Factory reference architecture, which covers the NVSwitch fabric, PCIe links, host CPUs, and the 1:1 pairing of GPUs with SuperNICs. For background on how an HBM stack is organized, use JEDEC JESD238.

D. Specialized units, performance, and framing

Covers the specialized engines, other noteworthy features, performance characterization, the framing slide, and the discussion questions.

The whitepaper describes the Decompression Engine, RAS Engine, Confidential Computing, and the second-generation Transformer Engine. Check its claims against §V-B of Jarmusch and Chandrasekaran, which measures decompressed output at roughly 160–220 GB/s, and against their §VII case studies. For FP4, the NVFP4 blog post explains NVIDIA’s format, but it is vendor-written.

The Blackwell architecture page is a short checklist of the same features: the RAS Engine, confidential computing with TEE-I/O, the second-generation Transformer Engine, and the Decompression Engine. It gives few numbers. For the Decompression Engine, the nvCOMP FAQ lists the supported formats (Snappy, LZ4, Deflate), the memory it can read, and the 4 MiB chunk limit on B200. For the Transformer Engine’s FP8 recipes, including MXFP8, use the FP8 scaling blog post. For confidential computing, the confidential computing blog post covers attestation and multi-GPU CC over NVLink, and measures the overhead. Its benchmarks ran on HGX B300, not B200. For partitioning one B200 into isolated instances, use the MIG page.

For performance, use MLPerf with care: cite the round, normalize per GPU, and note whether the comparison is at the same precision. Chips and Cheese (“Compute Throughput”, “Some Light Benchmarking”) and §VII-C1 of the 2026 Jarmusch paper cover the places where B200 does not improve on Hopper, such as FP64.

Where the sources disagree

  • HBM capacity. The Tuning Guide (§1.4.2.1) gives up to 180 GB, as does Table 1 of the HGX reference architecture; Jarmusch 2026 (§III-A) describes a unified 192 GB space. The gap is probably the difference between the full stack capacity and what is exposed on shipping parts, so state which figure you use and why.
  • Speedup breakdown. Jarmusch 2026 gives two breakdowns. For GEMM it attributes the gain to SM count (1.09×), tensor core efficiency (1.27×), and memory bandwidth (1.23×). For training (§VII-D) it attributes it to SM count (1.09×), CTA pairing (1.27×), and TMEM (1.26×). Cite the one that matches the workload.
  • Decompression throughput. The nvCOMP FAQ rates the Decompression Engine at up to 600 GB/s. Jarmusch 2026 (§V-B) measured about 160–220 GB/s of decompressed output. Treat 600 GB/s as a peak rating, not a measured result.
  • Confidential computing overhead. The confidential computing blog post headlines “98% of performance”, but its own Table 1 shows losses of 1% to 8%, measured on HGX B300. Quote the range and the platform.
  • GB203 versus B200. Results from Jarmusch 2025 come from a consumer part with no TMEM and a different FP64 rate. Do not apply them to B200 without saying so.
